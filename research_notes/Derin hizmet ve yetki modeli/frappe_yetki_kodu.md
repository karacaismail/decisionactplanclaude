Source of truth for every code claim below: the `version-16` branch of github.com/frappe/frappe, cloned on 16 November 2026. The branch head is commit `49789a1711d4dde2be9c6888efe35651465f4b64` (10 November 2026). This commit is exactly the tag `v16.56.0`, the latest v16 tag (`frappe/__init__.py` line 58 says `__version__ = "16.56.0"`). All permalinks below point to this commit. Base: `https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/`. The code was read only; no Frappe code was executed. Nothing here was tested on a running bench.

## Q1. Verification of the five earlier claims (verified table)

### Takeaway
Claims 2 and 4 are confirmed. Claim 3 is confirmed and is broader than thought: DocShare rows override a hook denial in single-document checks AND are OR-ed into list queries, and `disable_document_sharing` does not neutralise existing DocShare rows. Claim 1 is confirmed, but with a v16 change the docs do not show: in v16 a hook that returns `None` DENIES. Claim 5 is only partly true: Frappe Workflow transitions are role-gated but also accept a Python condition expression that can query the database.

### Cited Findings

**Claim 1. "has_permission hook can only deny, never grant."**
- `has_controller_permissions` docstring: "Controllers can only deny permission, they can not explicitly grant any permission that wasn't already present." — [permissions.py L483-L500](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/permissions.py#L483-L500)
- v16 loop: `for method in reversed(methods): ... if not controller_permission: return bool(controller_permission)` then `return True`. Any falsy result, including `None`, denies. All registered hooks (doctype-specific plus `"*"`) must return truthy — [permissions.py L494-L500](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/permissions.py#L494-L500)
- v15 loop was different: `if controller_permission is not None: return bool(controller_permission)`. In v15 `None` meant "no opinion" and the first non-None answer won — [permissions.py version-15 L455-L471](https://github.com/frappe/frappe/blob/2e9ecdc03fa5b5b8d1ba05224a1aff7dad832bd0/frappe/permissions.py#L455-L471)
- The v16 form (`if not controller_permission:`) is already present at tag v16.0.0 (line 482) and v16.20.0 (line 495) — checked by fetching raw files of those tags.
- The official hooks page still says: "If `None` is returned, it will fallback to default behaviour." This contradicts the v16 code — [Frappe hooks docs](https://docs.frappe.io/framework/user/en/python-api/hooks)
- When the hook denies, `get_doc_permissions` returns `{ptype: 0}` before role permissions are even read — [permissions.py L239-L241](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/permissions.py#L239-L241). When the hook allows, role permissions (DocPerm), `if_owner` and User Permissions still decide — [permissions.py L243-L282](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/permissions.py#L243-L282)
- The hook is only called when a document is passed. The doctype-level branch (`else:` with no `doc`) never calls it — [permissions.py L140-L177](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/permissions.py#L140-L177)
- Frappe's own hooks (ToDo, Event) always return an explicit bool, which fits the v16 rule — [todo.py L164-L172](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/desk/doctype/todo/todo.py#L164-L172), [event.py L298-L308](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/desk/doctype/event/event.py#L298-L308)

### Inferences
- The earlier report's sentence "Kayıt denetimi yalnız reddedebilir" is correct, but the operational rule must change: the hook must return `True` explicitly for allowed cases. A hook written in the v15 style ("return None when unsure") would lock everyone out on v16, and the official docs would not warn the team.
- The DocShare risk is larger than "sharing can re-grant after a hook denial". Shares also enter list results. The setting `disable_document_sharing` alone is not a full fix, because it does not ignore existing rows.
- Because lists skip the hook and records skip the list condition, the two must come from one source. Generate both from the same policy (for example, a function that returns a pypika Criterion for lists and a boolean for records). v16 now accepts a pypika term from `permission_query_conditions`, which makes this easier and safer than string SQL.

### Gaps
- No real v16 bench was run. Every "Test" column entry is a proposal.
- The exact pull request that changed the `None` semantics was not identified, because the clone was shallow. The change is present from v16.0.0.

## Q2. REST API, frappe.client, guests, API keys and OAuth

### Takeaway
All document REST routes call the same Document permission checks. `/api/resource` list goes through `frappe.client.get_list`, so the list rules (no hook, shares OR-ed) apply. OAuth bearer tokens become the full user: scopes are not enforced per endpoint. v16 also ships a built-in MCP endpoint that reuses the v2 API and is off by default.

### Cited Findings
- v1 routes: `GET /api/resource/<doctype>` calls `frappe.client.get_list`; `POST` runs `frappe.new_doc(doctype, **data).insert()`; `GET <name>` runs `check_permission("read")`; `PUT` runs `check_permission("write")` then `save()`; `DELETE` runs `frappe.delete_doc`; `POST <name>` with `run_method` runs a whitelisted document method after a read (GET) or write (POST) check — [api/v1.py L12-L152](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/api/v1.py#L12-L152)
- v2 routes (`/api/v2/document/...`) do the same; list uses `frappe.qb.get_query(..., ignore_permissions=False)` and lets a controller add a static `get_list(query)` — [api/v2.py L66-L240, L318-L323](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/api/v2.py#L66-L240)
- `/api/method/<path>` goes to `frappe.handler`; `is_whitelisted` refuses non-whitelisted functions and, for Guest, functions not marked `allow_guest=True` — [handler.py L65-L87](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/handler.py#L65-L87), [__init__.py L478-L496](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/__init__.py#L478-L496)
- `frappe.client.set_value`, `insert`, `save`, `submit`, `cancel` all go through `doc.save()/insert()/submit()`, so DocPerm, the hook, shares and `validate_workflow` apply. `set_value` blocks only standard fields — [client.py L183-L296, L528-L546](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/client.py#L183-L296)
- Guests: `/api/resource` has no login gate of its own; the list path calls `check_select_permission`, so a Guest sees data only if the Guest role has read/select on the doctype or a share exists for the Guest user (shares to "everyone" are excluded for Guest) — [query.py L1433-L1438](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/database/query.py#L1433-L1438), [share.py L201-L203](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/share.py#L201-L203)
- API keys: `Authorization: token key:secret` or `Basic base64(key:secret)` looks up an enabled User (or the doctype named in `Frappe-Authorization-Source`) and calls `frappe.set_user(user)`. The request then runs with all of that user's roles — [auth.py L700-L752](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/auth.py#L700-L752)
- OAuth bearer: `required_scopes` is read from the token's own `scopes` field and passed to `verify_request`; on success `frappe.set_user(<OAuth Bearer Token>.user)`. The scopes the token carries are the scopes it is checked against, so no endpoint-specific scope check happens — [auth.py L660-L697](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/auth.py#L660-L697)
- A header with two parts that fails all methods raises `AuthenticationError`; `restrict_ip` is enforced for API keys and bearer tokens since this version — [auth.py L634-L657](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/auth.py#L634-L657)

### Inferences
- The report's "İptal edilen cihaz ... dar bir yetkiye indirir" cannot rely on OAuth scopes. Frappe maps a bearer token to the full user. The product needs its own device check, for example in an `auth_hooks` function or inside the policy function, keyed by a device id carried with the token.

## Q3. Submittable documents, allow-on-submit, docstatus, ignore_permissions, db_set ("Tek komut yolu")

### Takeaway
DocPerm `create` and `submit` are checked on every insert, save and submit path, including REST and Workflow. `ignore_permissions` skips DocPerm, the hook and shares. `ignore_validate` skips `validate` and `before_submit`. `db_set` skips everything except `before_change` and `on_change`.

### Cited Findings
- `Document.has_permission` returns True at once if `self.flags.ignore_permissions` is set; no hook, no DocPerm, no share is evaluated — [document.py L640-L652](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L640-L652)
- `insert()` calls `check_permission("create")` before naming and before `before_insert` — [document.py L676-L760 (L715)](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L715)
- `_save()` calls `check_permission("write", "save")` — [document.py L822](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L822)
- `check_if_latest` calls `check_docstatus_transition`. Draft to submitted needs `submit`; submitted to submitted (update after submit) needs `submit`; submitted to cancelled needs `cancel`; cancelled cannot be edited. A NEW document inserted with `docstatus=1` takes the "submit" action and needs `submit` permission — [document.py L1355-L1427](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L1355-L1427)
- `run_before_save_methods`: `if self.flags.ignore_validate: return` before `validate` / `before_submit` run — [document.py L1661-L1695 (L1677, L1685)](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L1661-L1695)
- Update after submit: `validate_update_after_submit` rejects changes to fields without `allow_on_submit`, unless `flags.ignore_validate_update_after_submit` is set; new child rows in an allow-on-submit table pass — [document.py L1440-L1452](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L1440-L1452), [document.py L3310-L3330](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L3310-L3330)
- `db_set`: docstring "WARNING: This method does not trigger controller validations"; it calls `frappe.db.set_value` directly with no permission check, no `validate`, no allow-on-submit check; only `before_change` and `on_change` run — [document.py L1787-L1846](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L1787-L1846)
- `owner` and `creation` are overwritten by the server on insert (`self.owner = self.modified_by`), so a client cannot set the owner through REST — [document.py L1036-L1047](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L1036-L1047)
- `Document.update` drops only `doctype`, `flags`, `_parent_doc`, `_doc_before_save`, `_action`, `dont_update_if_missing` and cached properties. A REST body can therefore carry `name` and `docstatus` — [document.py L2317-L2345, L3636-L3646](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L3636-L3646)
- Doc events from `hooks.py` (`doc_events`) run through `run_method`, so they also fire inside `ignore_permissions` saves, but not when `ignore_validate` skips `validate`/`before_submit` — [document.py L1514-L1540, L1923-L1935](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/document.py#L1514-L1540)

### Inferences
- "Tek komut yolu" works as designed if user roles have no `create` and no `submit` DocPerm on decision doctypes. Then REST POST (with or without `docstatus=1`), REST PUT with `docstatus=1`, `frappe.client.submit`, `run_method=submit`, the desk form and Frappe Workflow all fail at the DocPerm layer.
- The custom endpoint must then insert/submit with `ignore_permissions=True`. That also skips the `has_permission` hook. So the endpoint must call the policy function itself before writing. `before_submit` still runs as the second layer, as long as the endpoint never sets `ignore_validate`.
- Ban `db_set`, `frappe.db.set_value`, `ignore_validate` and `ignore_validate_update_after_submit` on decision doctypes outside reviewed code; they bypass both layers.
- Users may still need `write` on submitted decisions only if allow-on-submit fields (for example the staleness mark) are edited by users. If only the server sets them, keep `write` off too and set them inside endpoints.

### Gaps
- `frappe.delete_doc` internals (link checks, `on_trash`, permission) were not read line by line.

## Q4. Does Frappe 16 keep a client-supplied UUID name?

### Takeaway
Yes. With DocType `autoname = "UUID"`, a client-supplied `name` that parses as a UUID is kept as-is; an empty name gets a server UUIDv7. Any UUID version is accepted, including v4 and v5.

### Cited Findings
- `set_new_name`: for autoname not in `("prompt", "uuid")` the name is reset to `None`; for `meta.autoname == "UUID"`: if no name, `doc.name = str(uuid7())`; if a `UUID` object, it is stringified; if a string, `UUID(doc.name)` must parse or `InvalidUUIDValue` is thrown; then the function returns before naming rules, `autoname` methods and `validate_name` — [naming.py L141-L198 (L158-L175)](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/naming.py#L141-L198)
- `uuid7` is imported from the standard library `uuid` module (`from uuid import UUID, uuid7`), which implies Python 3.14+ for v16 — [naming.py L10](https://github.com/frappe/frappe/blob/49789a1711d4dde2be9c6888efe35651465f4b64/frappe/model/naming.py#L10)

## Q5. Options for relationship-based access (ReBAC)

### Takeaway
At one site per tenant and small relation counts, an in-process policy function over Plan Üyeliği is enough and keeps decisions in the same database transaction. External engines (OpenFGA, SpiceDB) add a second write path and a consistency window; embedded engines (Cedar via cedarpy, Oso local authorization, Casbin) avoid the service but still need Frappe's two hooks to be generated from them. No public Frappe integration of any external authorization engine was found.

### Cited Findings
- OpenFGA consistency: default `MINIMIZE_LATENCY` "will serve queries from the cache when possible"; `HIGHER_CONSISTENCY` "will skip the cache and query the database directly". Caching is off by default, which makes every query strongly consistent. Zanzibar-style consistency tokens ("Zookies") are not in OpenFGA yet — [OpenFGA consistency](https://openfga.dev/docs/interacting/consistency)
- OpenFGA Check and ListObjects should agree "with some exceptions"; the Python SDK is autogenerated and supports StreamedListObjects from v0.9.1 — [OpenFGA list objects](https://openfga.dev/docs/getting-started/perform-list-objects.md), [Auth0 FGA consistency modes](https://docs.fga.dev/writing-data/consistency-modes)
- SpiceDB: `minimize_latency`, `at_least_as_fresh` (ZedToken), `at_exact_snapshot`, `fully_consistent`. Writes default to fully consistent; reads default to minimize latency. "A ZedToken is an opaque token representing a point-in-time"; ZedTokens address the New Enemy Problem and can be stored in a Postgres text column per resource — [SpiceDB consistency](https://authzed.com/docs/spicedb/concepts/consistency)
- SpiceDB has no general policy language for attribute rules, unlike Oso or Cedar — [Oso, SpiceDB alternatives](https://www-webflow.osohq.com/learn/spicedb-alternatives-authorization-tools-comparison) (vendor source, read via search snippet)
- Oso local authorization: "Oso does not read your data. Oso only needs to understand the schema." Facts are mapped to SQL in a YAML file; `listLocal` "Generates a SQL condition that filters a database query to only resources the actor is allowed to access". Supports PostgreSQL and MySQL — [Oso local authorization](https://www.osohq.com/docs/authorization-data/local-authorization)
- cedarpy: Python bindings for Cedar with `is_authorized`, `is_authorized_batch`, `validate_policies`; v4.12.2 maps to Cedar engine v4.12.0; "not officially supported by AWS or the Cedar Policy team"; early stage; batching cited as "+10x" faster; reusing a parsed PolicySet cuts parse cost about 9x — [cedar-py README](https://github.com/k9securityio/cedar-py). Separate packages `cedar-python` and `cedarling-python` exist and are different projects — [PyPI cedar-python](https://pypi.org/project/cedar-python/), [PyPI cedarling-python](https://pypi.org/project/cedarling-python/)
- Open edX (a Django platform) chose Casbin embedded through PyCasbin and rejected OpenFGA and SpiceDB as "overly complex for our current needs", citing "significant operational overhead" of a separate service — [Open edX ADR 0004](https://docs.openedx.org/projects/openedx-authz/en/latest/decisions/0004-technology-selection.html)
- Zanzibar scale (trillions of tuples, millions of checks per second) is far above one tenant site — [USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/pang) (as cited in the earlier report)
- A search for Frappe with OpenFGA, SpiceDB or Cedar found no integration — [web search, 16 November 2026, no Frappe-specific result]

### Inferences
- In-process policy function (recommended now): one module returns (a) a boolean for `has_permission`, (b) a pypika Criterion for `permission_query_conditions`, (c) a decision with reason for endpoints. Everything reads Plan Üyeliği in the same transaction and under the plan lock. No dual write, no cache window. Enough while each site has at most thousands of memberships.
- Embedded policy language (next step if rules grow): Cedar via cedarpy for record and endpoint decisions, but list filtering still needs hand-written SQL, because Cedar has no SQL generation (its partial evaluation is experimental). Oso local authorization generates SQL fragments, which maps directly onto `permission_query_conditions`, but it is a commercial cloud service plus a local library; check licensing before use.
- External ReBAC service (only if cross-site sharing or very large graphs appear): OpenFGA or SpiceDB per tenant store. Costs: Plan Üyeliği writes must also reach the engine (outbox pattern or after-commit job), a check made right after a membership change may be stale unless using HIGHER_CONSISTENCY or ZedTokens, every `get_list` needs ListObjects then an `IN (...)` filter, and the decision endpoint can no longer prove "authorised in the same transaction". Frappe also caches roles and user permissions in Redis, so a third cache layer adds more invalidation work.
- Whatever engine is used, the Frappe findings above still decide safety: hooks must return explicit True, list and record rules must match, DocShare must be blocked at `validate_share` and ignored in policy, and `ignore_permissions` writes must call the policy first.

### Gaps
- No measured latency numbers for OpenFGA or SpiceDB checks from Python were found in this session.
- Oso Cloud pricing and the licence of its local-authorization library were not checked.
- Cedar partial evaluation for SQL generation was not evaluated.
